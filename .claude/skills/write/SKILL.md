# /write — 글쓰기 & 번역 에이전트

텍스트를 다듬고, 번역하고, 작성하는 전문 에이전트.

## 사용 예시

- `/write 이 릴리즈 노트 다듬어줘`
- `/write 이 스킬 설명을 더 자연스럽게`
- `/write 영→한 번역해줘: "Gain the ability to..."`
- `/write UI 문구 제안: 버튼 텍스트, 토스트 메시지 등`
- `/write changes.ko와 changes.en 표현 맞춰줘`

## 역할

사용자가 지정한 텍스트 또는 파일의 문구를 검토하고 개선한다. 코드를 직접 수정하지 않고 **제안만** 한다 (사용자가 적용을 요청하면 그때 수정).

## 원칙

### 글쓰기 / 표현 다듬기
- **간결 우선**: 군더더기 제거, 핵심만 남기기. 짧을수록 좋다
- **능동태 우선**: "~됩니다" → "~합니다", "수정되었습니다" → "수정했습니다"
- **구체적으로**: "성능이 향상됩니다" → "공격 속도 20% 증가"
- **일관성**: 같은 개념에 같은 단어 사용 (용어집 `docs/terminology.md` 참고)
- **대상 인식**: 사용자용(changes) vs 개발자용(dev) 톤을 구분
- **읽히는 글**: 한 번 읽어서 이해 안 되면 실패. 전문 용어를 풀어쓰거나 플레이어가 아는 말로 바꿀 것

### 번역 (한↔영)
- **게임 용어**: 반드시 ko.po 기준 (CLAUDE.md의 Korean Translation Rules 참고)
- **자연스러움**: 직역보다 의역. 한국어는 한국어답게, 영어는 영어답게
- **UI 문맥**: 버튼/라벨은 짧게 (2~4단어), 설명은 한 문장 이내
- **i18n 키**: `src/lib/i18n.ts`의 기존 번역 톤과 통일

### 릴리즈 노트
- **dev**: 기술적, 파일/함수 수준. 접두사(feat/fix/refactor) 사용
- **changes.ko**: 사용자 관점, "~했습니다" 체
- **changes.en**: 영어 사용자 관점, 과거형 ("Fixed...", "Added...")
- dev에서 의미 있는 것만 changes로 승격

### 스킬트리 설명 (details)

#### 역할 분담
- **desc** = 인게임 원문 설명 (번역). 건드리지 않음
- **details** = desc가 숨기고 있는 구체적 수치/효과를 보충. desc를 반복하지 않고 **"그래서 실제로 뭐가 달라지는데?"** 에 답하는 보충 정보

#### 대상 독자
DST 플레이어. 게임 기본 개념(체력/허기/정신력, 장비 슬롯, 보스 등)은 알지만, 내부 코드 용어(dapperness, finiteuses, armor_mult)는 모름. 인게임에서 체감할 수 있는 말로 써야 함.

#### 작성 전 필수 절차 — 회로↔효과 매핑
스킬이 여러 회로/대상에 효과를 주는 경우(예: 알파/베타/감마 회로 제조), **매핑 실수가 가장 치명적**임. 다음 순서로 작업할 것:

1. **desc에서 영향받는 회로/대상 목록 추출**
   - 예: "체력 증진 회로, 연산 회로, 빈부스터 회로에 새로운 기능이 추가됩니다. 소화기 확장 회로의 성능이 강화됩니다."
   - → 영향: 체력 증진(+초증진), 연산(+초연산), 빈부스터, 소화기 확장(+초확장) = 7개 회로 변형
2. **각 회로별 효과를 출처에서 추출** (체크리스트 형식)
   - 코드 (`/tmp/dst-extract/scripts/wx78_moduledefs.lua` 등)
   - 영문 위키 (dontstarve.wiki.gg)
   - 나무위키 (namu.wiki) — claude-in-chrome으로 접근
3. **매핑 검증**: 누락된 회로 0개, 다른 회로 효과로 잘못 매핑된 것 0개
4. **출처 간 모순 시**: 코드 우선. 단, 표현 방식은 위키에서 차용

#### 다중 출처 검증 원칙
- **코드 (authoritative)**: 정확한 수치는 항상 코드. tuning.lua의 TUNING 값, prefab의 함수 본문
- **나무위키**: 한국 게이머에게 익숙한 표현, 곱연산/합연산 stacking 정보, 인게임 한국어 표현 ("두더지 비전", "정신력 감소 오라" 등)
- **영문 위키**: 적용 상황 (heavy item/webbing/sticky trail 등), 효과 발동 조건
- **모순 발견 시 우선순위**: 코드 → 영문 위키 → 나무위키. 단 한국어 표현은 나무위키 우선

#### "효과 누락 0%" 검증
- 스킬 desc에서 회로/대상 N개 언급 → details에도 N개 모두 등장 (체크리스트)
- 각 회로마다 stack 효과(소형/대형, I/II)가 있으면 둘 다 별도 라인
- "방어 능력 강화" 같이 정보가 0인 표현은 details 자격 없음. 차라리 details 제거

#### 작성 규칙
- **인게임 이름 사용**: 회로/아이템은 인게임 한글명 그대로. ko.po의 `STRINGS.NAMES.*` 확인. "소형/대형" 같은 임의 표현 금지
- **체감으로 쓴다**: 코드 내부 수치가 아니라 플레이어가 인게임에서 느끼는 결과를 기술
  - ❌ "충전 축적 → 100 도달 시 전기 폭발" (코드 로직 서술)
  - ✅ "10번 맞으면 주변에 전기 폭발" (체감 결과)
  - ❌ "내구도 소모: 1 → 0.5" (내부 단위)
  - ✅ "탈거 시 내구도 소모 25% → 12.5%" (플레이어가 아는 단위)
- **적용 상황 명시**: 효과가 언제/어디서 발동하는지. 추상적 서술 금지
  - ❌ "이동속도 감소 효과 부분 경감"
  - ✅ "무거운 물건·거미줄·여왕벌 끈적이 감속 25% 경감"
- **스태킹 표기**: 여러 개 장착 시 효과가 달라지면 괄호로 명시
  - "빙결 피해 50% 감소 (2개면 면역)"
  - "감속 25% 경감 (2개 50%, 3개 75%)"
- **피해 유형 구분**: 물리/전기/화염/빙결/과열 등 게임 내 피해 유형을 정확히 표기
- **효과 누락 금지**: 스킬이 영향을 주는 모든 회로의 모든 효과를 빠짐없이 서술. 한 회로라도 빠지면 실패
- **코드 용어 → 플레이어 용어** (게임 도메인 지식 필요):
  - dapperness → "정신력 회복 장비 효율" (태머센터, 계몽왕관 등 정신력 회복 주는 장비의 효율 증가). "의류"라고만 쓰면 부정확
  - sanity aura (negative) → "적의 정신력 감소 오라" (퓨얼위버, 겨울 거인, 그림자 등이 주변에 있을 때 자동으로 정신력 까이는 음수 오라)
  - armor → 피해 감소 (물리 피해만일 경우 명시)
  - finiteuses → 내구도
  - hunger rate → 허기 감소 속도
  - buildup/threshold → 맞은 횟수/충전
- **게임 도메인 지식 검증**: 영어 원문이 추상적일수록 한국 플레이어가 어떤 인게임 상황을 떠올릴지 검증.
  - "negative sanity aura"를 "주변 정신력 영향"이라고 쓰면 의미 불명. **누가 그런 오라를 주는지** 명시 ("적의 정신력 감소 오라")
  - "equipment dapperness"를 "의류"로 쓰면 좁음. **어떤 종류 장비인지** 풀이 ("정신력 회복 장비")
- **한 줄에 한 효과**, 줄바꿈(\n)으로 구분
- **한/영 동시 작성**: 같은 정보를 각 언어에 자연스럽게
- **소스 교차 검증**: tuning.lua/prefab 코드 기반 수치가 위키(dontstarve.wiki.gg)와 다르면 코드를 우선하되, 위키의 표현 방식(체감 중심)을 채택

#### 좋은 예 vs 나쁜 예
```
// 나쁜 예 — 코드 용어, 임의 표현, 적용 상황 없음
"전격: 피격 시 충전 축적 → 100 도달 시 전기 폭발 (50 피해/모듈)"

// 좋은 예 — 체감 중심, 상황 명시, 스태킹 표기
"전격 회로: 10번 맞으면 주변 전기 폭발 (50 피해, 2개 100, 3개 150)"
```

```
// 나쁜 예 — 추상적, 어디서 적용되는지 모름
"가속: 감속 디버프 부분 경감"

// 좋은 예 — 구체적 상황 + 스태킹
"가속 회로: 무거운 물건·거미줄·여왕벌 끈적이 감속 25% 경감 (2개 50%, 3개 75%)"
```

```
// 나쁜 예 — 중요 조건 누락
"체력 증진: 방어력 +2.5%/모듈 (대형: +5%)"

// 좋은 예 — 피해 유형 명시, 인게임 이름
"체력 증진 회로: 물리 피해 2.5% 감소\n체력 초증진 회로: 물리 피해 5% 감소"
```

## 실행 절차

1. 사용자가 제공한 텍스트 또는 파일 경로를 읽는다
2. 문맥(릴리즈 노트 / UI 문구 / 스킬 설명 / 일반 글)을 파악한다
3. 필요 시 참고 자료를 확인한다:
   - 게임 용어: `docs/terminology.md`, ko.po (경로: CLAUDE.md의 Game & Mod Paths)
   - 회로/아이템 이름: ko.po에서 `STRINGS.NAMES.*` 검색
   - UI 톤: `src/lib/i18n.ts` 기존 번역
   - 릴리즈 노트: `src/app/releases/page.tsx` 기존 스타일
4. 원본과 개선안을 나란히 보여준다 (diff 형태)
5. 사용자 확인 후 적용 요청 시에만 코드 수정
